How an outfit becomes a saved wear record

The browser selects clothes and displays results. The local Node service validates and saves them. Gemini generates garment illustrations; originals and results remain separate. This reference works offline without scripts or external services.

Three places to inspect

  1. Entry: public/app.js; search prepareWear, mutate and commitPending.

    After choosing garments and resolving a saved or new set, the browser makes one explicit save. A disconnected request keeps the same ID and full payload for retry.

  2. Rules: src/domain.mjs; find wear.record in applyAction.

    The same request creates one event. Another deliberate outfit change gets a new ID. Shared garments count once within an outfit. Events preserve the set membership snapshot even after archival.

  3. Storage: src/store.mjs, transaction and persist; then viewState in the domain module.

    Rules apply to a new snapshot. A temporary file replaces the saved file before in-memory state updates. Counts are derived from events, so removing a mistaken event also corrects related counts.

A reusable practice

Write down what “count once” means

Wearing the same top in two actual outfit changes counts twice. Retrying one interrupted save still counts once. The PRD defines these cases; the domain test named same deliberate save is idempotent; a separate same-day outfit counts again checks the distinction. Another project can start by writing two easily confused examples before choosing its deduplication rule.

The actual Gemini intake was checked separately. Automated storage/domain tests use isolated synthetic data. A mobile-sized browser and a physical phone are separate verification states.
